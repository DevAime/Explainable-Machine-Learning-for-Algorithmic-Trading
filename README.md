# SPY 5-Minute Explainable Trading Signal -- Research Project

DSA4900 thesis project. Trains a direction-prediction model on SPY
5-minute intraday data, generates SHAP explanations for its predictions,
and runs a within-subject human experiment testing whether seeing those
explanations changes how people make trading decisions -- including
whether it makes them *more accurately* trust the model (rely on it more
when it's right, less when it's wrong), not just more confident.

This document walks through the whole pipeline end to end: data ->
models -> explanations -> experiment -> statistical analysis. For setup
commands and file-by-file status, see the tables near the bottom; this is
the "how we actually did it and why" version.

---

## 1. Data

SPY 5-minute OHLCV bars from Alpaca, August 2022 -- July 2026 (~78,900
rows), regular trading hours only (09:30-16:00 ET). Diagnostics run before
any modeling: returns are stationary (ADF/KPSS confirmed); raw return
autocorrelation is statistically detectable but economically tiny
(~1.3% at lag 2) -- consistent with microstructure noise, not an
exploitable pattern. This is why XGBoost was chosen as the primary model
over a sequence model, with an LSTM kept as an *honest* comparison
baseline (expected to perform comparably, not assumed to win).

27 engineered features feed XGBoost (RSI, MACD, Bollinger Bands, ADX/DMI,
GARCH volatility, VIX, on-balance volume, session-time encodings, etc.) --
raw OHLCV price levels are excluded since they're non-stationary. The
LSTM uses a reduced 10-feature subset over a 24-bar (2-hour) lookback
window. Full feature list: `models/feature_list.json` (generated by
`models/features.py`).

## 2. Labeling

Target: 3-class direction (up / down / flat) of the return 12 bars (1
hour) ahead. Thresholds for "flat" are derived from the forward-return
distribution's own standard deviation (+/-0.5*std), not fixed arbitrary
values. Any label whose 12-bar horizon would cross into the next trading
day is **dropped, not imputed** (`models/labeling.py`).

## 3. Model training

`models/train_xgboost.py` and `models/train_lstm.py` both run **walk-
forward validation** (expanding window) under two retraining cadences --
weekly and monthly -- and report which generalizes better empirically,
rather than assuming one. On the full dataset: **monthly retraining won
for both models**, and with lower fold-to-fold variance too (not just a
better average) -- weekly's smaller test windows and less accumulated
training history between refreshes made it noisier, not just worse on
average. Final models are then trained on full history and saved to
`models/xgboost_model.json`, `lstm_model.h5` (+ `lstm_scaler.pkl`).

Actual result on the full dataset (`models/walk_forward_results.csv`,
monthly cadence):

| Model | Accuracy | F1 (macro) | Log loss |
|---|---|---|---|
| XGBoost | 0.5194 | 0.3358 | 1.0073 |
| LSTM | 0.4962 | 0.3657 | 1.1701 |

Read together with the accuracy diagnostic below (Section 8): both models
are only weakly better than chance at 3-class direction -- consistent
with the pre-modeling diagnostic that raw autocorrelation is real but
economically negligible. XGBoost edges out on accuracy/log-loss (likely
leaning more on the majority "flat" class); LSTM edges out on F1-macro
(more balanced across classes, less accurate overall). Neither
dramatically outperforms the other -- the "comparable, not assumed to
win" framing held up.

## 4. Explainability

SHAP `TreeExplainer` on the XGBoost model. Crucially, **explanations are
never computed live in the app** -- they're precomputed offline
(`experiment/generate_scenarios.py`) and served from a static file, so
the Streamlit app has zero dependency on xgboost/shap/tensorflow at
runtime (kept its deploy footprint light -- see `experiment/requirements.txt`).

## 5. Turning predictions into experiment scenarios

`experiment/generate_scenarios.py` builds the fixed set of 20 scenarios
the experiment uses, with one non-obvious but important design choice:
**each scenario is scored by the model that would have actually existed
at that point in walk-forward time**, not the final full-history model.
Concretely: for each walk-forward test fold, a *fresh* model is trained
on only that fold's training data, and both the prediction and the SHAP
explanation for that fold's scenarios come from that fold-specific model.
Using the final model instead would leak future training data into what's
supposed to be a "historical, out-of-fold" scenario.

The 20 scenarios are chosen to mix signal class (up/down/flat) and
confidence level (high/low), then split into two matched sets of 10
(Set A, Set B) for counterbalancing (next section). Each scenario stores:
the preceding ~2.5 hours of price bars (for the chart), the signal,
confidence, and the top-8 SHAP-contributing features relabeled into plain
language (e.g. `MACDh_12_26_9` -> "MACD momentum") -- saved once to
`experiment/scenarios.json`, loaded (never recomputed) by the app.

## 6. The experiment (Streamlit app)

<img width="707" height="606" alt="image" src="https://github.com/user-attachments/assets/e2793ce0-4809-4a67-bfa9-3b8e99d5803d" />


**Design:** within-subject, 2 conditions -- `explained` (signal + SHAP
shown) vs. `unexplained` (signal only). Every participant sees all 20
scenarios: trials 0-9 always `explained`, trials 10-19 always
`unexplained`. What's counterbalanced across participants is *which
scenario set* fills which slot, not the order of the conditions
themselves:

- **group_1**: Set A (explained, trials 0-9) -> Set B (unexplained, trials 10-19)
- **group_2**: Set B (explained, trials 0-9) -> Set A (unexplained, trials 10-19)

Group assignment is random per participant, stored in session state and
logged. **This is an important limitation to know going in**, not just
in hindsight: because every participant sees explained trials first and
unexplained trials second, "explained vs. unexplained" is confounded with
"first half vs. second half of the task" -- see Section 8.

**Trial flow**, identical structure every time (`experiment/app.py`,
`ui_components.py`): candlestick price chart (no future data visible) ->
model signal + confidence -> SHAP bar chart *only* in the explained
condition, plain-language feature names -> participant picks buy/hold/sell
and rates their confidence (1-5) -> timer runs from render to submit
-> immediate write to Google Sheets (see next section) -> forward-only
navigation, no back button, no outcome feedback shown (avoids trial-to-
trial learning contamination).

**Other design choices, all deliberate:** a consent screen (external
Google Form link) with a duplicate-participant-ID guard checked against
the Sheets log before a session can start; muted, restrained chart colors
(not default bright red/green) so color itself doesn't bias urgency
perception; pre-task instructions describe the task functionally ("for
some scenarios you'll also see what influenced the signal") without
revealing the actual research hypothesis.

**Two real bugs found and fixed post-launch, worth knowing about if you
extend this app:** (1) forcing a light background without forcing text
color made the whole page invisible for users whose browser/OS was in
dark mode -- fixed via `.streamlit/config.toml` forcing the theme, plus a
CSS text-color backstop; (2) candlestick charts spanning an overnight gap
(a scenario's lookback window crossing into the prior trading day)
rendered as a huge empty stretch because Plotly spaces bars proportional
to *real elapsed time* by default -- fixed by switching the x-axis to
categorical (evenly spaced by bar order, gaps just disappear), since nothing
here needs literal time-proportional spacing.

## 7. Data collection (Google Sheets)


`experiment/logging_utils.py` uses `gspread` + a Google Cloud service
account. Two tabs in one spreadsheet:

- **`trials`** -- one row per trial submission: participant ID, group,
  scenario ID, trial index, condition, signal shown, confidence shown,
  the participant's decision and confidence rating, response time.
  **Written immediately on every submission, never batched** -- so even
  an abandoned session leaves a complete record of whatever trials were
  actually finished.
- **`sessions`** -- one row logged at session *start* and another at
  session *completion*, so partial/abandoned sessions are distinguishable
  from completed ones by scanning for the latest status per participant.

Credentials branch automatically: a local JSON service-account key file
in dev, `st.secrets` on Streamlit Cloud (auto-detected by whether a
`gcp_service_account` secrets block exists, no manual env var needed).
The client is cached with `@st.cache_resource` so Streamlit's per-
interaction script reruns don't re-authenticate every time.

**Real-world attrition:** of 45 participants who started, 34 (75.6%)
completed all 20 trials, fairly evenly across group_1 (72.2%) and
group_2 (77.8%) -- so attrition doesn't look condition-dependent.

## 8. Statistical analysis

Done in a separate notebook against the downloaded Sheets export
(`trials` + `sessions` as xlsx). Full methodology:

**Ground truth reconstruction.** The Sheets data only has the model's
*predicted* signal, not what actually happened. To evaluate real decision
quality (not just agreement with the model), the actual 12-bar-forward
outcome for every scenario timestamp was reconstructed by re-running the
*exact same* labeling rule used in training (same `n_bars=12`, same
+/-0.5*std threshold, computed once from the full training return
distribution) against the real SPY price data. This lets every trial be
scored on three separate things: whether the model's shown signal was
actually correct (`model_correct`), whether the participant agreed with
what the model recommended (`agrees_with_model` -- a reliance measure),
and whether the participant's own decision matched reality
(`decision_correct` -- a real accuracy measure). These are three
genuinely different questions and conflating them was the main
methodological trap this design had to avoid.

**Model accuracy on the actual 20 shown scenarios: 45.0% (9/20 correct)**
-- notably underwhelming, though high-variance with only 20 scenarios.

**Cleaning.** Exact-duplicate trial submissions (same participant + trial
index logged twice, a double-click/rerun artifact) were deduped, keeping
the first. Analysis restricted to the 34 completers (20/20 trials) --
partial sessions were used only for the attrition summary, not the
inferential tests.

**Unit of analysis: paired at the participant level, not the trial
level.** Since every participant contributes both conditions, each
participant's 10 trials per condition were collapsed to a mean, then
compared with a paired t-test *and* a Wilcoxon signed-rank test
(confidence ratings are ordinal, response times are right-skewed, so the
nonparametric cross-check matters), plus Cohen's *d*z (the correct paired
effect-size formula: mean paired difference over the SD of the paired
differences). Trial-level mixed-effects linear models (random intercept
per participant) were run too, as a robustness check that doesn't
collapse to means.

**The core theoretical question wasn't just "did explanations change
behavior" but "did they change it appropriately"** -- an *appropriate
reliance gap* was computed per participant per condition: agreement rate
with the model when it was actually right, minus agreement rate when it
was actually wrong. A well-functioning explanation should push this gap
positive (trust it more when it's earned, less when it isn't).

### Results

| Measure | Explained | Unexplained | t-test p | Wilcoxon p | Cohen's *d*z |
|---|---|---|---|---|---|
| Confidence (1-5) | 3.28 | 3.12 | **0.0089** | **0.0081** | 0.48 (medium) |
| Response time (s) | 20.30 | 11.00 | **<0.0001** | **<0.0001** | 0.89 (large) |
| Agreement w/ model | 0.488 | 0.485 | 0.945 | 0.829 | 0.01 (~none) |
| Decision accuracy | 0.335 | 0.362 | 0.342 | 0.450 | -0.17 (small, ns) |
| Appropriate reliance gap | 0.016 | 0.020 | 0.954 | 0.979 | -0.01 (~none) |

Mixed-effects models corroborated the paired tests independently:
`confidence_rating ~ condition` gave an unexplained-condition coefficient
of -0.165 (p=0.003); `decision_correct ~ condition` gave +0.026 (p=0.469,
not significant).

**Interpretation.** Explanations reliably made people more confident and
slower to decide (the two clearest, most robust effects) -- but they
didn't change *what* people decided, whether people followed the model's
advice more, or whether their decisions were actually more accurate. Most
importantly for the paper's core question: there's **no evidence
explanations improved appropriate reliance** -- participants didn't
discriminate any better between trusting a correct signal and doubting an
incorrect one when they could see why the model made its call. Combined
with the model's own so-so accuracy (45%) and participant accuracy
hovering near chance (33-36%) in both conditions, the honest reading is
that explanations changed the *feel* of the task (more confidence, more
deliberation) without changing the *substance* of decision quality.

**Limitation to report explicitly, not bury:** condition is confounded
with trial order -- every participant saw explained trials first,
unexplained second, regardless of group (only the scenario-set mapping
was counterbalanced, not the condition sequence). The response-time
effect especially could partly reflect practice/fatigue rather than a
pure causal effect of explanations. N=34 completers is also modest for
detecting small effects, particularly the reliance-gap null result, which
may partly reflect low power rather than a true zero effect.

## Repository layout

```
model_2/
  data/                        SPY 5-min OHLCV + engineered features (parquet)
  models/
    labeling.py                 3-class target construction, day-boundary exclusion
    features.py                 XGBoost (27) / LSTM (10) feature list definitions
    walk_forward.py             weekly/monthly expanding-window fold generation
    train_xgboost.py            trains + validates XGBoost, picks better cadence
    train_lstm.py                trains + validates LSTM (early stopping, GPU-friendly)
    xgboost_model.json, lstm_model.h5, lstm_scaler.pkl, feature_list.json
    walk_forward_results.csv     per-fold metrics, both models, both cadences
  experiment/
    generate_scenarios.py        builds scenarios.json (fold-specific out-of-fold models)
    scenarios.json                the 20 precomputed scenarios the app serves
    app.py                       Streamlit app: consent -> trials -> thank-you
    config.py                    study params, colors, plain-language feature names
    scenarios.py                  loads scenarios.json, builds counterbalanced sequences
    ui_components.py              chart/SHAP-chart/progress rendering
    logging_utils.py              Google Sheets logging (gspread, dev/deployed branching)
    requirements.txt              lightweight, deploy-only (no xgboost/tensorflow/shap)
    .streamlit/config.toml        forces light theme (dark-mode text bug fix)
  requirements.txt               full pipeline deps (training + experiment)
```

## Setup & running

```bash
pip install -r requirements.txt
```

**1. Train the models** (run in order, from `models/`):
```bash
python train_xgboost.py
python train_lstm.py
```
Produces `walk_forward_results.csv` -- check it to see which cadence
actually generalized better on your data before assuming monthly (what
we found) generalizes.

**2. Generate experiment scenarios** (from `experiment/`, run once,
offline, after training):
```bash
python generate_scenarios.py
```

**3. Run the experiment app locally**:
```bash
streamlit run app.py
```
Needs a Google Cloud service account JSON key at
`experiment/credentials/gsheets_creds.json` (gitignored) for local dev,
or `st.secrets["gcp_service_account"]` configured for Streamlit Cloud
deployment (auto-detected, no manual toggle). Replace the placeholder
`CONSENT_FORM_URL` in `config.py` with your real Google Form link before
sending it to participants.

**4. Analyze collected data**: export the Google Sheet as xlsx, then work
through ground-truth reconstruction -> cleaning -> descriptive stats ->
paired tests -> mixed-effects models, per Section 8 above (notebook not
included in this repo -- built interactively; ask if you want it
regenerated here).
